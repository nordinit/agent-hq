# Agent teams

Status: **implemented, not deployed.** Migration `21-agent-teams.sql` is written and verified but
has been applied to scratch databases only — never to `agent_hq_prod`. See "As built" at the end
for what shipped, where it deviates from this plan, and what deploying it requires.

## The problem this solves

Agent HQ today has 68 agents, 44 workflows, and **496 rows in `sprint_task_routing_rules`** —
roughly eleven routing rules per workflow, hand-maintained. Every new workflow re-declares the
same "implementer → reviewer → releaser" shape, and every agent that participates carries its
own private copy of the tool, skill, and MCP assignments that the shape implies.

There is also nothing in an agent's prompt that tells it who else is working the same
workflow. `buildTaskMessage()` gives it the workflow goal, project context, its own
`job_instructions`, and the task. It does not know that Casper reviews what it writes, so it
cannot hand off deliberately — it can only move a status and hope routing does the right thing.

A **team** is the missing noun: a named group of agents with a shared goal, mutual awareness,
a default capability bundle, and a reusable routing shape that can be stamped onto a workflow.

## Model

```
teams  ──< team_members >──  agents
  │
  ├──< team_tool_assignments >── tools
  ├──< team_mcp_assignments >── mcp_servers
  ├──  teams.skill_names (JSON, mirrors agents.skill_names)
  └──< team_routing_rules            (templates, keyed by workflow_type)
              │
              │  materialize on assignment
              ▼
       sprint_task_routing_rules  (with source_team_id provenance)
              ▲
              │
    sprints.team_id  ── a workflow is owned by at most one team
```

Four capabilities, in the order they should be built:

1. **Mutual context** — each member's prompt carries the team goal, its own role, and every
   teammate's role.
2. **Capability defaults** — tools, skills, and MCP servers granted to the team flow to every
   member.
3. **Workflow ownership** — a workflow is assigned a team.
4. **Routing defaults** — the team's routing template is stamped onto workflows it owns.

## 1. Schema

One new migration. **Take the number from the deploy repo, not this worktree** — production has
`20-runtime-executions-and-checkpoints.sql` applied, which does not exist in
`db/pg-migrations/` here. This checkout is the public `nordinit` mirror; `mband0` main is the
deploy source. Writing `21-*.sql` against this tree's `19-*` high-water mark would collide.

### Vocabulary

New tables use **workflow** vocabulary, not sprint. Migration `14-routing-config-audit-log.sql`
already set this precedent (`workflow_type`, `workflow_id` columns on a brand-new table, written
to be idempotent across both namings). The staged rename in
`db/pg-migrations/staged/10-rename-legacy-terminology.sql` is still unapplied — live tables are
still `sprints`, `sprint_task_routing_rules` — so the new tables must *reference* the old names
while *naming their own columns* with the new ones.

This is why team↔workflow ownership is a **column on `sprints`**, not a join table: a join table
would need a `sprint_id` column, which the regenerated rename mapping would then rewrite,
leaving a new table straddling both vocabularies for no benefit.

### Tables

```sql
CREATE TABLE teams (
  id bigint GENERATED BY DEFAULT AS IDENTITY,
  tenant_id bigint NOT NULL,
  name text NOT NULL,
  slug text NOT NULL,
  description text NOT NULL DEFAULT '',   -- operator-facing blurb
  goal text NOT NULL DEFAULT '',          -- INJECTED into every member's prompt
  charter text NOT NULL DEFAULT '',       -- INJECTED: shared standards / working agreements
  project_id bigint,                      -- optional scoping, mirrors agents.project_id
  skill_names text NOT NULL DEFAULT '[]', -- mirrors agents.skill_names
  context_version bigint NOT NULL DEFAULT 1,
  enabled bigint NOT NULL DEFAULT 1,
  created_at text NOT NULL DEFAULT ...,
  updated_at text NOT NULL DEFAULT ...,
  deleted_at text,
  PRIMARY KEY (id)
);
-- UNIQUE (tenant_id, slug) WHERE deleted_at IS NULL

CREATE TABLE team_members (
  id bigint GENERATED BY DEFAULT AS IDENTITY,
  team_id bigint NOT NULL,
  agent_id bigint NOT NULL,
  member_role text NOT NULL DEFAULT '',      -- "Implementer" — INJECTED
  responsibilities text NOT NULL DEFAULT '', -- "writes and lands code changes" — INJECTED
  is_lead bigint NOT NULL DEFAULT 0,
  is_primary bigint NOT NULL DEFAULT 0,      -- tiebreak when an agent is on several teams
  sort_order bigint NOT NULL DEFAULT 0,
  enabled bigint NOT NULL DEFAULT 1,
  created_at text NOT NULL DEFAULT ...,
  PRIMARY KEY (id)
);
-- UNIQUE (team_id, agent_id)

CREATE TABLE team_tool_assignments (
  id, team_id, tool_id, overrides text NOT NULL DEFAULT '{}', enabled bigint NOT NULL DEFAULT 1
);  -- shape-identical to agent_tool_assignments

CREATE TABLE team_mcp_assignments (
  id, team_id, mcp_server_id, overrides text NOT NULL DEFAULT '{}', enabled bigint NOT NULL DEFAULT 1
);  -- shape-identical to agent_mcp_assignments

CREATE TABLE team_routing_rules (
  id bigint GENERATED BY DEFAULT AS IDENTITY,
  tenant_id bigint NOT NULL,
  team_id bigint NOT NULL,
  workflow_type text,        -- NULL = applies to any workflow type
  task_type text,            -- NULL = any, matching sprint_task_routing_rules semantics
  status text NOT NULL,
  agent_id bigint,           -- must be a member of team_id (validated)
  member_role text,          -- alternative target: resolve to the member holding this role
  priority bigint NOT NULL DEFAULT 0,
  enabled bigint NOT NULL DEFAULT 1,
  created_at text, updated_at text,
  PRIMARY KEY (id)
);
-- CHECK (agent_id IS NOT NULL OR member_role <> '')
```

`member_role` targeting is what makes a team template portable: a "Standard delivery squad"
template routes `in_review → Reviewer`, and swapping which agent holds Reviewer does not
require editing rules.

### Columns on existing tables

```sql
ALTER TABLE sprints ADD COLUMN team_id bigint;                     -- FK teams(id) ON DELETE SET NULL
ALTER TABLE sprint_task_routing_rules ADD COLUMN source_team_id bigint;       -- provenance
ALTER TABLE sprint_task_routing_rules ADD COLUMN source_team_rule_id bigint;  -- provenance
```

Both provenance columns are `ON DELETE SET NULL`: deleting a team must not delete the routing
rules a workflow is actively running on. The rules become locally-owned, which is the correct
failure mode.

## 2. Context injection

The highest-value part of the idea, and the lowest-risk to build — both prompt assemblers are
pure functions with existing unit tests.

### Where the text goes

New module `api/src/services/dispatch/prompt/teamContext.ts`:

```ts
export function buildTeamContextSection(team: {
  name: string;
  goal: string;
  charter: string;
  members: Array<{ name: string; memberRole: string; responsibilities: string; isSelf: boolean; isLead: boolean }>;
}): string
```

Rendered block:

```
--- Team: Delivery Squad ---
Goal: Ship the billing migration with no customer-visible downtime.

You are Nova — Implementer. You write and land the code changes.

Your teammates:
- Piper — Planner (lead). Breaks work into tasks and sets acceptance criteria.
- Casper — Reviewer. Reviews diffs and gates on tests, risk, and budget.

Working agreements:
<charter>

Hand work to a teammate by recording the outcome that routes to them. Do not do a
teammate's role yourself.
--- End Team ---
```

Two insertion points, both trivial:

| Site | File | Change |
|---|---|---|
| Task dispatch | `api/src/services/dispatch/prompt/taskMessage.ts:1` | new optional `teamContext` param, prepended before `job_instructions` |
| Review / summary dispatch | `api/src/services/dispatcher.ts:2290` (`buildDispatchMessage`) | new optional `teamContext` field, emitted after `[Workflow Goal]`, before project context |

Callers to thread it through: `api/src/scheduler/reconciler.ts:437` and
`api/src/domains/sprints/lifecycle.ts:106`.

### Which team

Resolver `getTeamContextForDispatch(db, { agentId, sprintId })` in `api/src/domains/teams/context.ts`:

1. The workflow's `sprints.team_id`, **if the agent is a member of it**. (This is the case the
   whole feature is aimed at.)
2. Otherwise, the agent's only enabled membership.
3. Otherwise, the membership flagged `is_primary`.
4. Otherwise nothing — inject no block, and log the ambiguity rather than guessing.

Case 1 deliberately requires membership. An agent pulled in as a one-off on a team-owned
workflow should not be told it is on a team it is not on; that produces prompts that describe
handoffs the agent cannot actually perform.

### Ordering and observability

Members render in `(sort_order, id)` order so the block is byte-stable across dispatches — churn
here would defeat prompt caching on every run. `teams.context_version` bumps on any change to
the team, its membership, or a member's role text; the resolved `team_id` and `context_version`
go into `job_instances.payload_sent` so a transcript can be tied back to exactly the team
definition it ran under.

`GET /api/v1/teams/:id/context-preview?agent_id=N` returns the exact rendered block. Worth
building on day one — it turns "why did the agent do that" into a one-request answer.

### Runtime placement

v1 puts the block in the **dispatch message**, which works identically across every runtime
(openclaw, claude-code, hermes, webhook, custom). A later refinement can promote it to a system
prompt for claude-code — `appendSystemPromptFilePath` is already plumbed in
`api/src/runtimes/claudeCode/args.ts:104` but nothing populates it today.

## 3. Capability defaults

Team-granted tools, skills, and MCP servers **union** with the agent's own; the agent-level row
wins on conflict, and an agent-level assignment with `enabled = 0` is an explicit opt-out from a
team grant. This falls out of the existing `enabled` column on both assignment tables — no new
concept needed.

One new module, `api/src/domains/teams/effectiveCapabilities.ts`, exporting the effective
resolvers, then swap call sites:

| Call site | What it reads today |
|---|---|
| `api/src/runtimes/toolInjection.ts:35` `fetchAgentTools` | `agent_tool_assignments` |
| `api/src/runtimes/mcpMaterialization.ts:664, :1626` | `agent_mcp_assignments` |
| `api/src/runtimes/claudeCode/mcpConfig.ts:239` | `agent_tool_assignments` |
| `api/src/bin/agent-tool-mcp.ts:143, :155` | `agent_tool_assignments` |
| `api/src/services/dispatcher.ts:1535` | `agents.skill_names` |

`agent-tool-mcp.ts` is the one that is easy to miss and expensive to get wrong: it is the
standalone MCP server that actually *exposes* registry tools to a running agent. If it resolves
a different set than the dispatcher materialized, the agent sees tools it was not granted or
loses tools it was.

**Tenant isolation.** `fetchAgentTools` already joins `t.tenant_id = a.tenant_id` and logs
suppressed cross-tenant assignments. Team-provided tools need the same guard on the same terms —
a team in tenant A must not be able to hand a tool to an agent in tenant B. There is an existing
test file, `api/src/routes/capabilityTenantIsolation.test.ts`, that should grow a team case.

`agent_mcp_capability_policies` follows the same inherit-and-override pattern, but can be
deferred to a follow-up; it is a narrower surface than the three above.

## 4. Workflow assignment and routing defaults

`sprints.team_id` assigns a team to a workflow. Assignment alone changes context injection
(section 2). Routing is a **separate, explicit action** — silently rewriting 496 rows' worth of
routing configuration as a side effect of setting a dropdown is not acceptable.

### Materialize, don't resolve

When a team's routing template is applied to a workflow, expand `team_routing_rules` into real
`sprint_task_routing_rules` rows stamped with `source_team_id` / `source_team_rule_id`.

The alternative — extending `resolveRoutingRuleForSprint` (`api/src/domains/routing/rules.ts:41`)
with a team fallback tier — is cleaner in the abstract and worse in practice here. Routing
precedence is consumed by `scope.ts`, `trace.ts`, `preview.ts`, `graph.ts`, `audit.ts`,
`policy/`, and the reconciler's `resolveRoutedTaskAgentId`
(`api/src/scheduler/reconciler.ts:271`), each with its own tests. A new tier means touching all
of them, and the Routing UI would still show nothing until it was taught about the tier
separately. Materialization leaves every one of those paths byte-identical and makes team rules
visible in the tool operators already use.

The cost is drift, and drift is handled by making it visible rather than by preventing it:

- `POST /api/v1/workflows/:id/team/apply-routing?dry_run=1` returns the diff — created,
  updated, conflicting, orphaned. The dry-run and preview conventions already exist
  (`routing.dryRun.test.ts`, `routing.preview.test.ts`); follow them.
- Applying writes `routing_config_audit_log` rows under a shared `batch_id`, which is what that
  table's `batch_id` and `affected_workflow_count` columns were built for.
- A rule whose local values diverge from its source template is reported as a conflict and left
  alone. Operator edits win over the template.
- The Routing page shows a "from team X" provenance badge, and flags divergence.

This mirrors how `default_package_applications` already records
`created_json` / `restored_json` / `updated_json` / `conflicts_json` — the same shape of problem
with the same shape of answer.

### Rule resolution at apply time

For each `team_routing_rules` row whose `workflow_type` matches the target workflow's
`sprint_type` (or is NULL):

- `agent_id` set → use it, after validating the agent is still an enabled member.
- `member_role` set → resolve to the enabled member holding that role. Zero matches is a
  reported skip, not a silent no-op; more than one is an error surfaced in the dry run.

## 7. Phasing

| Phase | Scope | Ships value |
|---|---|---|
| 1 | Migration, teams + members CRUD, MCP domain, minimal UI | Teams exist and are editable |
| 2 | Context injection + context-preview endpoint | **The core idea.** Agents know their team |
| 3 | Effective capability resolution across the five call sites | Stop copying tool/skill/MCP sets per agent |
| 4 | `sprints.team_id`, routing templates, dry-run apply, provenance | Stop hand-writing 11 rules per workflow |
| 5 | UI polish, divergence reporting, docs | Operable |

Phase 2 before 3 and 4 on purpose: it is pure-function work with the highest ratio of behavior
change to blast radius, and it is independently useful even if routing templates are never
built.

## 8. Risks

- **Migration numbering** — production is at 20; this worktree shows 19. Number from `mband0`
  main.
- **Staged rename collision** — `staged/10` and `staged/11` are unapplied. New tables must carry
  no `sprint_*` identifiers, or the regenerated rename mapping will rewrite them.
- **`agent-tool-mcp.ts` divergence** — the standalone tool server must resolve the same
  effective set as the dispatcher, or granted and exposed tools disagree at runtime.
- **Prompt bloat** — a 15-member team with prose responsibilities is a meaningful token tax on
  every dispatch. Cap rendered members and truncate `responsibilities`; consider rendering only
  members reachable from the current task's routing graph once teams get large.
- **Cross-tenant capability leakage** — teams are a new path into `tools` and `mcp_servers` and
  need the tenant guard `fetchAgentTools` already applies.
- **Deleting a team** must not orphan a running workflow: soft-delete, `ON DELETE SET NULL`
  provenance, materialized rules survive as locally-owned.

## 9. Decisions

Settled, 2026-08-05:

1. **Routing defaults materialize with provenance.** Team templates expand into real
   `sprint_task_routing_rules` rows stamped `source_team_id` / `source_team_rule_id`. Every
   existing routing path stays untouched. Drift surfaces as a dry-run diff; operator edits to a
   materialized rule win over the template and are reported as conflicts, never overwritten.
2. **Capabilities union, agent wins.** Effective set is team grants ∪ agent grants; an
   agent-level row overrides the team's config for the same tool or server, and an agent row
   with `enabled = 0` is an explicit opt-out from a team grant.
3. **One team per workflow.** `sprints.team_id`, nullable. A join table can be added later if
   multi-team demand appears; it is deliberately not built now because it would carry a
   `sprint_id` column into the pending rename.

Still open, and safe to defer — the resolver in section 2 handles either answer:

- **Multi-team agents.** Assumed allowed, with the active team resolved from workflow ownership
  (falling back to sole membership, then `is_primary`). If teams should instead be exclusive,
  that becomes a `UNIQUE (agent_id)` on `team_members` and steps 2–4 of the resolver collapse.

## As built

Implemented 2026-08-05. Every phase in the table above landed. 169 API suites / 1606 tests pass,
`tsc --noEmit` is clean in both packages, and both packages build.

### Deviations from the plan above

**1. A third provenance column.** The plan promised "a rule whose local values diverge from its
source template is reported as a conflict and left alone", which `source_team_id` and
`source_team_rule_id` cannot actually deliver: once a materialized rule differs from its template,
"the operator edited the rule" and "the template changed" are the same observation and need
opposite handling. `sprint_task_routing_rules.source_team_applied_json` records the values written
at the last apply, which separates them:

| Current row vs. snapshot | Snapshot vs. template | Result |
|---|---|---|
| same | same | `unchanged` |
| same | differs | `update` — resync |
| differs | — | `conflict` — the operator edited it, local wins |

**2. Multi-team agents are allowed** (the open question in section 9 is now decided). An agent may
join any number of teams; a partial unique index enforces at most one `is_primary` membership per
agent, which keeps the dispatch-time tiebreak total.

**3. `requestAuditActor` moved** from `routes/routing.ts` into `domains/routing/audit.ts`. Two
routers now audit routing configuration, and the identity policy it encodes should not be
duplicated.

| Concern | Location |

| Team resolution at dispatch | `api/src/domains/teams/context.ts` |

| UI | `ui/app/teams/`, `ui/components/WorkflowTeamCard.tsx`, `ui/components/AgentTeamsCard.tsx` |

`domains/teams/effectiveCapabilities.ts` imports only a type from `db/adapter`. That is load-bearing:
`api/src/bin/agent-tool-mcp.ts` deliberately does not import `runtimes/toolInjection` (it would drag
the runtime directory and the SDK into every process mounting that server), so placing the shared
resolver in `domains/` is what lets the standalone tool server and the dispatcher resolve the same
set without duplicating the query.

### Deploying it

1. **The migration number is only correct in the deploy repo.** Production is at
   `20-runtime-executions-and-checkpoints.sql`, which does not exist in this worktree — this
   checkout is the public `nordinit` mirror and `mband0` main is the deploy source. Confirm 21 is
   still free there before applying.
2. This worktree cannot boot against production regardless: `verifyMigrationsCurrent` treats
   migration 20 as `unexpected` — recorded but absent from this release — and refuses to serve.
   That is pre-existing, not caused by this work.
3. Nothing is retroactive. No team exists until one is created, `resolveTeamContextForDispatch`
   returns null for every agent, and the effective-capability resolvers reduce to exactly the
   agent-level queries they replaced. Existing dispatches are byte-identical until an operator
   creates a team and adds members.
